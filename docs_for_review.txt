TỔNG HỢP TÍNH NĂNG: QUẢN TRỊ ADMIN (ADMIN CONTROL-PLANE)
DỰ ÁN: MINDGEM
===============================================================================

1. TỔNG QUAN (OVERVIEW)
-------------------------------------------------------------------------------
Tính năng Quản trị Admin (Admin Panel / DB Control Plane) là hệ thống trung tâm 
dành riêng cho quản trị viên (người dùng có quyền role === "admin") trong dự án 
MindGem. System này cho phép Super Admin theo dõi toàn bộ hệ thống 
theo thời gian thực, quản lý hồ sơ người chơi, thao tác điều chỉnh điểm số các 
trục nhận thức, xử lý dữ liệu và quản trị tài khoản người dùng.

Các khả năng chính của tính năng Admin:
- Giao diện Control Plane chuyên biệt: Cyberpunk / Database Dashboard với hiệu ứng 
  neon, hiển thị trạng thái kết nối Supabase, độ trễ cơ sở dữ liệu (DB Latency) 
  và tổng số lượng người dùng (profiles).
- Quản lý người dùng & Bảng dữ liệu Live Data Grid: Hiển thị danh sách toàn bộ 
  người chơi (`public.profiles`) với các thông số điểm trục (Logic, Memory, Speed, 
  Focus, Spatial), XP và số lượt chơi (Sessions).
- Điều chỉnh điểm chỉ số & XP (Admin Grant): Cho phép cộng thêm (`add`) hoặc 
  gán đè (`set`) điểm số cho 5 trục nhận thức và điểm kinh nghiệm (Total XP) của 
  bất kỳ người dùng nào, hỗ trợ nút bấm nhanh preset (10, 50, 100, 500, 1000).
- Reset điểm số (Reset Scores): Đưa toàn bộ điểm chỉ số 5 trục, XP và số liệu 
  phiên chơi của người dùng được chọn về 0.
- Xóa tài khoản vĩnh viễn (Danger Zone / Delete User): Xóa hoàn toàn người dùng 
  bao gồm Avatar lưu trữ ở Supabase Storage, Auth Account trong Supabase Auth 
  và thông tin Profile trong cơ sở dữ liệu Postgres.
- MFA Required (Bảo mật 2FA): Yêu cầu quản trị viên phải xác thực 2 bước (MFA). Mọi hành động chỉnh sửa/xóa đều phải qua hàm `requireAdmin` kiểm tra `aal === "aal2"` trong JWT.
- Nhật ký hoạt động (Activity Log): Theo dõi log thao tác console client-side của phiên bản Admin hiện hành.


2. KIẾN TRÚC HỆ THỐNG (ARCHITECTURE)
-------------------------------------------------------------------------------
Mô hình triển khai tách biệt giữa Client (React / Next.js UI) và Server (Supabase 
Edge Functions running Deno + Hono Framework), giao tiếp qua HTTPS RESTful API.

[ Client UI Layer ] 
  └─ AdminPanel (Container / Controller)
       ├─ AdminShell (Theme Shell & Layout Grid)
       ├─ AdminOverview (System Telemetry & Metrics)
       ├─ AdminControls (Grant / Reset / Delete Forms)
       ├─ ProfilesGrid (Live User Table)
       ├─ ActivityLog (Console Log Monitor)
       └─ AccessDenied (Security Fallback Guard)

[ Client API Layer ]
  └─ src/app/lib/api/admin.ts (SDK wrappers using serverPost)

[ Server Edge Layer ]
  └─ supabase/functions/server/routes/admin.ts (Hono API endpoints)
       ├─ POST /server/admin-grant  (Apply points/XP)
       ├─ POST /server/admin-reset  (Zero out scores)
       └─ POST /server/admin-delete-user (Purge Auth + Storage + Profile)

[ Database & Auth Layer ]
  ├─ Supabase Auth (admin.deleteUser)
  ├─ Supabase Storage (bucket: "avatars")
  ├─ Postgres Table: public.profiles
  └─ Postgres RPC: sync_achievements_for(p_user)

4. CHI TIẾT TRIỂN KHAI (IMPLEMENTATION DETAILS)
-------------------------------------------------------------------------------
A. KIỂU DỮ LIỆU VÀ MAPPING CỘT (TYPES & COLUMN MAPPING):

- Kiểu chế độ grant (GrantMode):
  `type GrantMode = "add" | "set";`

- Kiểu giá trị form grant (GrantAxes):
  `type GrantAxes = Record<AxisKey, string>;`
  với `AxisKey = "logic" | "memory" | "speed" | "focus" | "spatial"`

- Payload gửi tới server (AdminGrant):
  ```typescript
  type AdminGrant = {
    axes?: Partial<Record<AxisKey, number>>;
    xp?: number;
    mode?: "add" | "set";
  };
  ```

- Mapping từ AxisKey sang Cột Database (AXIS_COLUMNS):
  - logic   -> `algebraic_logic_score`
  - memory  -> `memory_score`
  - speed   -> `speed_score`
  - focus   -> `focus_score`
  - spatial -> `spatial_score`

B. HẰNG SỐ VÀ CÁC NGƯỠNG AN TOÀN (CONSTANTS & BOUNDS):

- Bảng màu Admin Control-Plane (ADMIN_COLORS):
  - green:  "#00FF9C" (Màu chủ đạo neon)
  - blue:   "#00D4FF" (Màu chỉ số / latency)
  - amber:  "#F59E0B" (Màu cảnh báo / XP)
  - red:    "#F43F5E" (Màu nguy hiểm / xóa)
  - purple: "#A855F7" (Màu target user / selected)

- Ngưỡng giới hạn điểm số trục (Axis Bounds):
  `[0, 1000]` điểm. Mọi phép cộng/gán đều được kẹp (clamp) bằng công thức:
  `nextScore = Math.max(0, Math.min(1000, Math.round(calculatedScore)))`

- Ngưỡng giới hạn XP (XP_MAX Bound):
  `XP_MAX = 200,000,000` (200 triệu XP, tương ứng level ~2000).
  Edge Function chỉ làm tròn delta bằng `Math.round(calculatedDelta)`. Ràng buộc biên nằm ở RPC admin_grant_tx — chặn abs(delta) > 10,000,000 và chặn tổng sau khi cộng vượt XP_MAX = 200,000,000.
  *Lý do thiết kế*: Tránh trường hợp Admin gõ nhầm nhiều chữ số 0 làm `total_xp` 
  vượt quá giới hạn, đẩy level lên hàng triệu và làm hỏng Bảng xếp hạng.

C. THUẬT TOÁN & LOGIC XỬ LÝ CHÍNH:

1. Logic tính toán Grant (Thêm / Gán điểm):
   - Nếu `mode === "set"`: Giá trị mới = `amount`
   - Nếu `mode === "add"`: Giá trị mới = `current_score + amount`
   - Kẹp vào khoảng `[0, 1000]` cho 5 trục. Với XP, truyền thẳng `delta` xuống RPC `admin_grant_tx`. RPC sẽ chặn cứng lỗi với `abs(delta) > 10,000,000` hoặc nếu tổng vượt `200,000,000`.

2. Tự động đồng bộ Huy hiệu / Thành tựu (Badge Auto-Sync):
   Khi XP được cập nhật thành công qua Admin Grant, server chủ động gọi RPC:
   `await adminClient.rpc("sync_achievements_for", { p_user: targetId });`
   Giúp huy hiệu của người dùng được cập nhật ngay lập tức mà không phải chờ 
   người dùng tự mở bảng thành tựu.

3. Logic Reset Scores:
   Gọi RPC `admin_reset_stats`:
   ```sql
   admin_reset_stats(p_target uuid, p_actor uuid)
   -- stats_epoch = now()
   -- 5 trục = 0, session counters = 0
   -- last_active_date = now()   -- tránh decay tối đa ngay sau reset, fix lỗi daysSince(null)
   -- KHÔNG xóa xp_events (ngoại trừ game = \'achievement\' để tránh double XP) (giữ audit trail)
   ```



4. Logic Xóa tài khoản Triệt để (3-Tier Account Purge):
   - Bước 1: Liệt kê và xóa toàn bộ file ảnh đại diện trong Supabase Storage bucket 
     `avatars` tại thư mục `${targetId}/*`.
   - Bước 2: Gọi Supabase Auth Admin API để xóa người dùng khỏi hệ thống xác thực:
     `await adminClient.auth.admin.deleteUser(targetId);`
     Nếu DB có thiết lập FK `ON DELETE CASCADE`, profile sẽ tự động bị xóa.
   - Bước 3: Đảm bảo tính an toàn (fallback), gọi lệnh xóa trực tiếp trong DB:
     `await adminClient.from("profiles").delete().eq("id", targetId);`
   - Chống tự xóa: Server kiểm tra `if (targetId === user.id)` và từ chối xóa với 
     mã lỗi HTTP 400 (`Use delete-account for your own account`).

5. Console Log Buffer & DB Latency Telemetry:
   - Client duy trì mảng `log` chứa tối đa 60 dòng gần nhất, định dạng 
     `[HH:mm:ss] Action details`.
   - Đo thời gian query DB thực tế bằng `performance.now()` khi fetch leaderboard.
   - `AdminOverview` có hiệu ứng sóng nhịp tim (pulse wave) cập nhật qua 
     `setInterval` 1400ms dùng hàm lượng giác: `Math.sin((index + beat) * 0.9)`.

6. BẢO MẬT & VALIDATION (SECURITY & VALIDATION)
-------------------------------------------------------------------------------
1. Phân quyền Phòng thủ Đa tầng (Multi-Layer Defense in Depth):
   - Tầng UI Client: Kiểm tra `profile.role === "admin"`. Nếu không phải admin, 
     hệ thống chặn không render panel mà hiển thị giao diện `<AccessDenied />`.
   - Tầng Client SDK: Mọi hàm tác vụ trong `admin-panel.tsx` đều có guard clause 
     `if (!isAdmin || busy) return;`.
   - Tầng Server Authentication: Endpoint gọi `authenticatedUser(c)` để xác thực 
     JWT bearer token từ header request.
   - Tầng Server Authorization: Endpoint gọi `requireAdmin(c)` để truy vấn 
     bảng `profiles` kiểm tra cột `role === 'admin'` và đồng thời kiểm tra token 
     JWT xem `aal === 'aal2'` (MFA). Nếu vi phạm, lập tức từ chối bằng mã lỗi 
     HTTP 403 Forbidden.

2. Sử dụng Service Role (Admin Client):
   Server Edge Function dùng `adminClient` (khởi tạo với `SUPABASE_SERVICE_ROLE_KEY`) 
   để có quyền tối cao bypass RLS khi thực hiện các tác vụ quản trị hệ thống và 
   thao tác với Supabase Auth Admin SDK.

3. Kẹp biên Dữ liệu & Chống ô nhiễm (Input Sanitation & Bounds Enforcement):
   - Hàm `parseGrantField()` loại bỏ khoảng trắng, kiểm tra `Number.isFinite()`, 
     chỉ chấp nhận giá trị số hợp lệ.
   - Kẹp biên 5 trục chỉ số trong khoảng `[0, 1000]`.
   - RPC sẽ lo phần giới hạn an toàn của XP delta và tổng XP. Mọi giá trị delta vô lý đều bị từ chối ở tầng database.

4. Chống Tự Xóa Tài khoản Không An Toàn:
   Server kiểm tra `if (targetId === user.id)` trong route `admin-delete-user` 
   để ngăn Admin dùng nhầm route xóa người dùng khác nhằm tự xóa chính mình, bắt 
   buộc phải dùng quy trình `delete-account` cá nhân chuẩn để dọn dẹp session.

5. Audit Logging (Ghi vết kiểm toán):
   Các thao tác can thiệp dữ liệu như `admin.grant` và `admin.reset` được ghi log 
   server bất biến thông qua bảng `admin_audit` (ADR-0006) với thông tin chi tiết: 
   actor (ID của Admin thực hiện), target_id, action, details (axes, xp) và 
   timestamp. Bảng này lưu trữ 365 ngày để phục vụ điều tra.

TÀI LIỆU TỔNG HỢP TÍNH NĂNG: CHỐNG GIAN LẬN & QUAN SÁT HỆ THỐNG
(ANTI-CHEAT & OBSERVABILITY) - DỰ ÁN MINDGEM
================================================================================

1. TỔNG QUAN (OVERVIEW)
--------------------------------------------------------------------------------
Tính năng Chống gian lận (Anti-cheat) và Quan sát hệ thống (Observability) cung cấp cơ chế bảo vệ tính toàn vẹn điểm số của trò chơi huấn luyện nhận thức MindGem, đồng thời giám sát sức khỏe hệ thống từ Client đến Server Edge Functions.

- Chống gian lận (Anti-cheat):
  + Nguyên tắc cốt lõi: "Thà lọt còn hơn bắt oan" (Better to miss a cheater than ban an innocent player).
  + Kiểm tra toàn bộ dữ liệu đo đạc hành vi (telemetry - thời gian phản ứng, nhịp bấm, số lượt chạm...) phía Server trước khi tính điểm và cấp XP.
  + Phân loại cờ gian lận thành 2 mức:
    * Hard Flags: Từ chối ván chơi ngay lập tức (HTTP 422), đốt vé chơi (round ticket) để chống tấn công dò ngưỡng (oracle attack), ghi log vi phạm nghiêm trọng vào database.
    * Soft Flags: Vẫn chấp nhận ván chơi và tính điểm bình thường, nhưng ghi nhận cảnh báo nghi vấn vào hệ thống theo dõi mức độ tin cậy.

- Quan sát hệ thống (Observability):
  + Cung cấp giải pháp giám sát tập trung, chuẩn hóa log và vết lỗi cho cả Client (Browser) và Server (Supabase Edge Functions).
  + Ghi log cấu trúc dạng một dòng JSON (structured single-line JSON) giúp lọc và đếm sự kiện trực tiếp trên dashboard.
  + Định danh từng request bằng requestId (Header `x-request-id`) xuyên suốt từ Client -> CDN -> Middleware -> Router -> DB.
  + Tự động làm sạch dữ liệu cá nhân (PII Redaction: ẩn JWT, API keys, password, email, UUIDs, chuỗi số dài).
  + Đẩy dữ liệu lỗi/sự kiện từ Client về Server theo lô (batching) với cơ chế chống spam (rate limiting) và khử trùng lặp (deduplication).
  + Lưu trữ các sự kiện warn/error/fatal vào bảng database `observability_events`.


2. KIẾN TRÚC HỆ THỐNG (ARCHITECTURE)
--------------------------------------------------------------------------------
Hệ thống được chia làm 2 tầng chính:

A. Tầng Client (Browser / React App):
   - `src/app/lib/logger.ts`: Bộ bọc (wrapper) logger toàn ứng dụng.
     + Trong môi trường DEV: In ra console trình duyệt.
     + Trong môi trường PROD: Tắt hoàn toàn console log để tránh rò rỉ thông tin hệ thống, tự động điều hướng lỗi (`logError`) và cảnh báo (`logWarn`) sang module observability.
   - `src/app/lib/observability.ts`: Trình thu thập lỗi và sự kiện độc lập (pure JS).
     + Tự động lắng nghe sự kiện toàn cục: `window.onerror`, `unhandledrejection`, `visibilitychange`, `pagehide`.
     + Quản lý hàng đợi bộ nhớ (in-memory queue), gom lô tối đa 20 sự kiện / 10 giây.
     + Khử trùng lặp lỗi trong cửa sổ 60 giây bằng thuật toán hash djb2.
     + Làm sạch PII dữ liệu trước khi gửi.
     + Gửi dữ liệu theo phương thức HTTP POST đến endpoint `/server/telemetry` sử dụng `fetch` với `keepalive: true`.

B. Tầng Server (Supabase Edge Functions - Deno & Hono Framework):
   - `supabase/functions/_shared/anticheat.ts`: Mô-đun anti-cheat thuần (pure functions), chứa toàn bộ các quy tắc kiểm tra thời gian thực và hành vi người chơi cho 12 trò chơi.

4. CHI TIẾT TRIỂN KHAI (IMPLEMENTATION DETAILS)
--------------------------------------------------------------------------------

A. BỘ KIỂM TRA ANTI-CHEAT (`inspectRound` TRONG `_shared/anticheat.ts`)
--------------------------------------------------------------------------------
Các hằng số & hàm toán học cơ bản:
- `HUMAN_FLOOR_MS = 80`: Ngưỡng sàn thời gian phản ứng vật lý tối thiểu của con người (80ms).
- `ROBOT_CV = 0.04`: Hệ số biến thiên (Coefficient of Variation $CV = \sigma / \mu$) tối thiểu. Nếu $CV < 0.04$ khi số mẫu $N \ge 10$, nhịp thao tác bị coi là quá đều đặn như máy móc (metronomic / bot). Hàm `cv(xs)` sẽ tự động trả về `1.0` nếu có ít hơn 10 mẫu để tránh false positive.
- Các hàm thống kê: `median(xs)`, `mean(xs)`, `cv(xs)`, `nums(v)` (lọc lấy danh sách số hợp lệ $\ge 0$).

Hàm kiểm tra chung (Shared Inspectors):
1. `inspectShared(t, serverElapsedMs)`:
   - So sánh `t.timeMs` (thời gian client khai báo) với `serverElapsedMs` (thời gian Server đo từ lúc tạo ticket).
   - Nếu `timeMs - serverElapsedMs > 5000ms` -> Cờ **soft** ("Client time far exceeds server elapsed").
2. `inspectSubThreshold(t, game)`:
   - Tìm các mẫu thời gian phản ứng nằm trong khoảng cận trên của ngưỡng người $[80ms, 120ms)$.
   - Nếu số mẫu trong khoảng này chiếm $\ge 50\%$ tổng số mẫu -> Cờ **soft** ("Majority of reaction times below 120ms").

Chi tiết kiểm tra từng trò chơi (12 Game Inspectors):
1. `reaction` (Phản ứng nhanh):
   - Cỡ mẫu $N < 3 \to$ Không kiểm tra.
   - Lấy danh sách mẫu $< 80ms$ (`below`). Nếu `below.length >= 3` và tỷ lệ `below / total >= 40%` -> Cờ **hard** ("Multiple reactions below human floor"). Ngược lại nếu `below.length > 0` -> Cờ **soft** ("Isolated sub-floor reaction").
   - Các mẫu rác (`< HUMAN_FLOOR_MS`) sẽ bị loại bỏ khỏi luồng tính `median` và `cv` để giảm false positive.
   - Nếu `median(rts) < 130ms` -> Cờ **hard** ("Reaction median impossibly low").
   - Nếu `cv(rts) < 0.04` -> Cờ **soft** ("Reaction timing too metronomic").
2. `schulte` (Bảng Schulte):
   - Cỡ mẫu $N < 4 \to$ Không kiểm tra.
   - Nếu `median(hitRts) < 150ms` -> Cờ **hard** ("Schulte hit median impossibly low").
   - Nếu `cv(hitRts) < 0.04` -> Cờ **soft** ("Schulte timing too metronomic").
3. `stroop` (Thử thách Stroop):
   - Cỡ mẫu $N < 4 \to$ Không kiểm tra.
   - Nếu `median(rts) < 200ms` -> Cờ **hard** ("Stroop median impossibly low").
   - Nếu `cv(rts) < 0.04` -> Cờ **soft** ("Stroop timing too metronomic").
4. `sudoku` (Điền số Sudoku):
   - Với các bước di chuyển (`moveRts.length >= 5`):
     * Nếu `median(moveRts) < 120ms` -> Cờ **hard** ("Sudoku move median impossibly low").
     * Nếu `cv(moveRts) < 0.04` -> Cờ **soft** ("Sudoku timing too metronomic").
   - Kiểm tra cấp độ: Nếu `difficulty` là "Master" hoặc "Extreme" và `timeMs < 45.000ms` (45 giây) -> Cờ **soft** ("Sudoku expert board finished too fast").
5. `memory` (Ghi nhớ chuỗi):
   - Lấy `clearedLevels` (hoặc fallback `maxLevel`).
   - Nếu `cleared < 3` -> Bỏ qua (không kết luận vì quá ít dữ liệu, tránh bắt oan người chơi thua ở cấp 1-2).
   - Thiếu `totalTaps` -> tối đa chỉ cờ **soft** ("Memory pace implausibly fast (estimated)"). Sẽ update `TELEMETRY_SCHEMA_VERSION` thành 2 khi nào front-end gửi được `totalTaps`, lúc đó mới được hard reject.

6. `nback` (Ghi nhớ N-Back):
   - Cỡ mẫu $N < 3 \to$ Không kiểm tra.
   - Nếu `median(rts) < 150ms` -> Cờ **hard** ("N-Back median impossibly low").
   - Nếu `cv(rts) < 0.04` -> Cờ **soft** ("N-Back timing too metronomic").
7. `math` (Tính nhẩm nhanh):
   - Cỡ mẫu $N < 4 \to$ Không kiểm tra.
   - Nếu `median(rts) < 250ms` -> Cờ **hard** ("Math median impossibly low").
   - Nếu `cv(rts) < 0.04` -> Cờ **soft** ("Math timing too metronomic").
   - Nếu `difficulty === "hard"`, trả lời đúng toàn bộ (`correct === totalProblems`), và `median(rts) < 1200ms` -> Cờ **soft** ("Perfect hard math finished too fast").
8. `gonogo` (Ức chế phản xạ Go/No-Go):
   - Với $N \ge 3$: Nếu `median(rts) < 160ms` -> Cờ **hard**; `cv(rts) < 0.04` -> Cờ **soft**.
   - Kiểm tra ức chế hoàn hảo: Nếu `nogoTrials >= 8`, `goTrials >= 16`, không có lỗi bấm nhầm (`falseAlarms === 0`), đúng toàn bộ lượt Go (`hits === goTrials`), số mẫu $N \ge 12$, và `median(rts) < 220ms` -> Cờ **soft** ("Perfect inhibition with very fast Go RTs").
9. `mental` (Xoay hình không gian):
   - Với $N \ge 4$: Nếu `median(rts) < 250ms` -> Cờ **hard** ("Mental Rotation median impossibly low"); `cv(rts) < 0.04` -> Cờ **soft**.
   - Hoàn hảo siêu tốc: Nếu `trials >= 16`, `correct === trials`, $N \ge 12$, và `median(rts) < 450ms` -> Cờ **soft** ("Perfect mental rotation finished too fast").
10. `corsi` (Thử thách Corsi Block):
    - Với $N \ge 4$: Nếu `median(rts) < 180ms` -> Cờ **hard** ("Corsi tap median impossibly low"); `cv(rts) < 0.04` -> Cờ **soft**.
    - Kỷ lục chuỗi: Nếu `span >= 8` và số lần thử `trials <= span` -> Cờ **soft** ("Corsi span very high with too few trials").
11. `trail` (Nối điểm Trail Making):
    - Với $N \ge 5$: Nếu `median(rts) < 200ms` -> Cờ **hard** ("Trail Making hop median impossibly low"); `cv(rts) < 0.04` -> Cờ **soft**.
    - Quét điểm hoàn hảo: Nếu `nodes >= 20`, `wrongClicks === 0`, và `timeMs < nodes * 260ms` -> Cờ **soft** ("Perfect trail finished implausibly fast").
12. `search` (Tìm kiếm đối tượng):
    - Nếu điểm số `score > 80` -> Cờ **soft** ("search: score exceeds human limits").
    - Nếu $N \ge 10$ và `cv(rts) < 0.04` -> Cờ **soft** ("search: mechanically steady pace (robot)").

Đảm bảo kiểu dữ liệu toàn diện (Exhaustive Registry):
`GAME_INSPECTORS satisfies Record<Game, GameInspector>` bắt buộc mọi Game mới thêm vào enum `Game` phải có hàm inspector tương ứng, nếu thiếu sẽ báo lỗi TypeScript ở thời điểm biên dịch.

Quy trình xử lý tại Route `/server/submit-round`:
- Gọi `inspectRound(gameId, telemetry, serverElapsedMs)`.
- Khi dính **Hard Flag**:
  + **Đốt ticket lập tức**: Cập nhật `round_tickets.submitted_at = new Date().toISOString()` trước khi phản hồi HTTP 422. Việc này triệt hạ khả năng biến anti-cheat thành Oracle thử lại (retry oracle attack).
  + Ghi lại từng hard flag vào DB bằng RPC `record_cheat_flag(p_user_id, p_game, p_reason, p_severity, p_details)`.
  + Ghi log server cảnh báo `anticheat.hard_reject`.
  + Trả về lỗi HTTP 422 Unprocessable Entity: `{ error: "Round rejected: suspicious timing patterns.", code: "anticheat_hard", flags: ["timing_patterns_rejected"] }`.
- Khi dính **Soft Flag**:
  + Duyệt qua danh sách soft flags và gọi RPC `record_cheat_flag` lưu vết vào DB.
  + Ván chơi **vẫn tiếp tục** được tính điểm, tính XP và lưu kết quả bình thường.


B. LÀM SẠCH VÀ BẢO VỆ DỮ LIỆU CÁ NHÂN (REDACTION PII)
--------------------------------------------------------------------------------
Cả phía Client và Server đều áp dụng các quy tắc lọc PII (Personally Identifiable Information) và Secret Keys nghiêm ngặt thông qua mảng `REDACTIONS`:

Danh sách Regex Lọc (`REDACTIONS`):
1. Chuỗi JWT: chuỗi regex -> `"[jwt]"`
2. Các khóa bảo mật / Token: `/(apikey|api_key|access_token|refresh_token|token|secret|password|authorization)(\s*[:=]\s*)[^\s,;"'}]+/gi` -> `"$1$2[redacted]"`
3. Địa chỉ Email: chuỗi regex -> `"[email]"`
4. Mã định danh UUID: `/\b[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}\b/gi` -> `"[uuid]"`
5. Chuỗi số dài (>= 9 chữ số): chuỗi regex -> `"[num]"`

Hàm xử lý:
- `scrubText(input, maxLen = 300)`: Chuyển đối tượng thành chuỗi, áp dụng lần lượt mảng `REDACTIONS`, chuẩn hóa khoảng trắng dư thừa và cắt ngắn chuỗi nếu dài quá `maxLen` kèm ký tự `…`.
- `scrubContext(context)`: Giới hạn tối đa 20 đối tượng key-value, tên key tối đa 40 ký tự. Các giá trị kiểu `number`, `boolean`, `null` được giữ nguyên; giá trị dạng văn bản/đối tượng khác được chạy qua `scrubText`. Tổng độ dài văn bản được quản lý theo ngân sách ký tự (budget $\le 2000$).


C. QUẢN LÝ REQUEST ID VÀ LOG CẤU TRÚC SERVER (`_shared/observability.ts`, `middleware.ts`)
--------------------------------------------------------------------------------
- Cấp phát Request ID:
  + Dùng `WeakMap<Request, string>` để lưu giữ requestId tương ứng với từng HTTP Request object.
  + Hàm `beginRequest(req)`: Kiểm tra header ưu tiên từ CDN (`x-request-id` hoặc `cf-ray`). Nếu không có, tự động sinh UUID mới bằng `crypto.randomUUID()`.
  + Phía Middleware: Gán header `x-request-id` vào `Response` trả về cho Client.
- Ghi Log dạng Cấu trúc (`logRequest`, `logServerEvent`):
  + In log dưới dạng 1 dòng JSON duy nhất qua `console.log(JSON.stringify(line))`.
  + Các trường chuẩn: `ts`, `level` (`debug` | `info` | `warn` | `error` | `fatal`), `event`, `requestId`, `method`, `path`, `status`, `durationMs`, `context`.
  + Lưu trữ bền vững (Persistence):
    * `logRequest`: Tự động ghi vào bảng `observability_events` khi `status >= 500` hoặc `status === 429` hoặc `status === 422`.
    * `logServerEvent`: Tự động ghi vào DB khi `level` thuộc nhóm `warn`, `error`, `fatal` (hoặc cờ `persist: true`).


D. QUẢN LÝ LỖI ỨNG DỤNG (`AppError` & `middleware.ts`)
--------------------------------------------------------------------------------
- Lớp `AppError`:
  ```ts
  export class AppError extends Error {
    constructor(
      message: string,
      readonly status: 400 | 401 | 409 | 410 | 422,
      readonly code: string,
    ) {
      super(message);
      this.name = "AppError";
    }
  }
  ```
- Giúp ánh xạ chuẩn xác các HTTP status code chuyên biệt (400 Invalid Game/Payload, 401 Unauthorized, 409 Already Submitted, 410 Expired Ticket, 422 Anti-cheat Reject) mà không bị rơi vào kịch bản bắt lầm regex biến lỗi validation thành lỗi 401 (khiến client tự động đăng xuất người dùng).
- Bộ xử lý ngoại lệ toàn cục (`app.onError` trong `middleware.ts`): Bắt tất cả các lỗi chưa được xử lý (unhandled exception), log sự kiện `http.unhandled_error` level `error` và trả về JSON 500 chuẩn `{ error: "Internal error", requestId }`.


E. OBSERVABILITY VÀ LOGGER PHÍA CLIENT (`src/app/lib/observability.ts`, `src/app/lib/logger.ts`)
--------------------------------------------------------------------------------
- Module `logger.ts`:
  + Khi ở môi trường DEV (`import.meta.env.DEV === true`): Cho phép in ra console thông thường (`console.error`, `console.warn`, `console.info`).
  + Khi ở Production: Vô hiệu hóa toàn bộ console log để ngăn rò rỉ tên bảng, tên cột, truy vấn Postgres trong DevTools. Chuyển hướng `logError` sang `captureError` và `logWarn` sang `captureMessage`.
- Thư viện `observability.ts`:
  + Quản lý bởi bộ thu thập `Collector` (`createCollector`).
  + Khử trùng lặp lỗi (Deduplication): Tạo dấu vân tay (fingerprint) bằng thuật toán hash djb2 từ chuỗi `(event | level | normalizedMessage | route)`. Nếu lỗi trùng lặp xuất hiện lại trong vòng 60 giây (`DEDUPE_WINDOW_MS = 60_000`), hệ thống chỉ tăng biến đếm `count` chứ không gửi lại sự kiện rác.
  + Tự động đăng ký lắng nghe sự kiện trình duyệt trong `initObservability()`:
    * `window.onerror`: Bắt lỗi JavaScript runtime chưa được try/catch.
    * `window.onunhandledrejection`: Bắt lỗi Promise reject không có `.catch()`.
    * `visibilitychange` (khi trang bị ẩn) & `pagehide`: Tự động gọi `flush()` để gửi toàn bộ sự kiện còn trong queue đi lập tức.
    * Đặt lịch định kỳ: `setInterval(() => sink.flush(), 10.000)` (mỗi 10 giây flush 1 lần).
  + Gom lô (Batching): Đẩy tối đa 20 sự kiện / 1 lô request.
  + Phiên làm việc (Session): Tự động cấp và lưu trữ `sessionId` ngẫu nhiên trong `sessionStorage` với key `neurobics.obs.session`.


F. ROUTE TIẾP NHẬN TELEMETRY VÀ RATE LIMITING (`supabase/functions/server/routes/telemetry.ts`)
--------------------------------------------------------------------------------
- Endpoint: `POST /server/telemetry` (Public, không yêu cầu Authorization token vì lỗi thường xảy ra trước khi có phiên đăng nhập).
- Các lớp bảo vệ:
  1. Rate Limiting: Khai báo `createRateLimiter({ limit: 60, windowMs: 60_000 })`. Giới hạn tối đa 60 request / 1 phút / 1 địa chỉ IP (`x-forwarded-for`). Khi vượt ngưỡng, trả về HTTP 202 `{ ok: true, dropped: true }` im lặng để không làm hỏng trải nghiệm client.
  2. Giới hạn kích thước Body: Kiểm tra độ dài chuỗi JSON `raw.length > 32.000` bytes (32KB) -> Trả lỗi HTTP 413 `Payload too large`.
  3. Giới hạn số lượng sự kiện: Hàm `sanitizeClientEvents` cắt tối đa 20 sự kiện / lô payload.
  4. Chống giả mạo danh tính (Identity Spoofing Protection): Mọi đối tượng sự kiện từ Client gửi lên đều bị đè trường `user_id: null`. Client không được tự khai báo danh tính trên endpoint công khai này. Việc đối soát người dùng sẽ dựa trên `session_id` hoặc so khớp `request_id` với các log server.


5. LUỒNG DỮ LIỆU (DATA FLOW)
--------------------------------------------------------------------------------

A. LUỒNG CHƠI VÁN & KIỂM TRA ANTI-CHEAT (`submit-round`):
1. Người chơi hoàn thành ván -> Client gửi `POST /server/submit-round` chứa `{ roundId, game, telemetry, fingerprint }`.
2. Middleware nhận request -> Cấp/trích xuất `x-request-id` -> Đánh dấu mốc thời gian bắt đầu request.
3. Router `rounds.ts` xác thực Auth Token người dùng -> Truy vấn DB lấy vé chơi `round_tickets`.
4. Server đo thời gian thực đã trôi qua: `serverElapsedMs = Date.now() - ticket.started_at`.
5. Chạy hàm kiểm tra `inspectRound(gameId, telemetry, serverElapsedMs)`:
   - NẾU DÍNH HARD FLAG:
     * Cập nhật ngay `round_tickets.submitted_at = now()` (đốt ticket).
     * Gọi RPC `record_cheat_flag` lưu chi tiết cờ Hard vào DB.
     * Log sự kiện cảnh báo server `anticheat.hard_reject`.
     * Trả về HTTP 422 `{ error: "Round rejected: suspicious timing patterns.", code: "anticheat_hard", ... }`.
   - NẾU CHỈ DÍNH SOFT FLAG HOẶC HỢP LỆ:
     * Duyệt mảng Soft flags và gọi RPC `record_cheat_flag` cho từng cờ.
     * Liên kết thiết bị nếu có fingerprint qua RPC `link_device`.
     * Gọi `scoreAndValidate` để tính điểm chuẩn xác.
     * Gọi RPC `submit_round_transaction` cập nhật các trục nhận thức, điểm số và XP vào DB.
     * Trả về HTTP 200 kèm dữ liệu kết quả ván chơi & mảng `cheatFlags`.
6. Middleware `finally` block thực hiện log JSON dòng `http.request` chứa `durationMs` và HTTP status code.

B. LUỒNG GHI LOG OBSERVABILITY TỪ CLIENT VỀ SERVER:
1. Xuất hiện lỗi ở Client (hoặc gọi `logError`/`logWarn`) -> Đẩy thông tin vào `observability.ts`.
2. Hàm `scrubText` & `scrubContext` tiến hành xóa PII (JWT, email, token) -> Tính fingerprint bằng djb2 -> Kiểm tra khử trùng lặp trong 60 giây.
3. Sự kiện hợp lệ được đưa vào Hàng đợi (Queue).
4. Khi Queue đủ 20 sự kiện hoặc sau 10 giây (hoặc khi người dùng đóng/ẩn tab) -> Client gọi `fetch(".../server/telemetry", { keepalive: true })`.
5. Server `telemetry.ts` tiếp nhận request -> Kiểm tra Rate Limit theo IP (60/phút) -> Kiểm tra Body $\le 32KB$ -> Sanitization dữ liệu & ép `user_id = null` -> Chèn mảng dòng log vào bảng database `observability_events`.


6. BẢO MẬT & VALIDATION (SECURITY & VALIDATION)
--------------------------------------------------------------------------------
- Chống tấn công dò ngưỡng Anti-cheat (Anti-cheat Oracle Prevention): Đốt ticket (`submitted_at = now()`) lập tức trước khi phản hồi HTTP 422. Kẻ gian không thể sử dụng lại ticket để thử lại nhiều lần nhằm dò tìm mốc thời gian vừa đủ qua mặt hệ thống.
- Chống giả mạo danh tính (User Identity Spoofing Protection): Endpoint `/server/telemetry` tuyệt đối không tin tưởng field `userId` từ client gửi lên và luôn đè thành `null`.
- Cấu hình CORS an toàn: Chỉ cho phép danh sách Origin được duyệt (`ALLOWED_ORIGINS`) và hạn chế danh sách Header (`Content-Type`, `Authorization`, `apikey`, `x-client-info`).
- Giới hạn hạn ngạch (Rate Limiting):
  + Tạo vé ván chơi (`start-round`): Tối đa 20 ván bắt đầu trong 1 phút (`MAX_TICKET_STARTS_PER_MINUTE`) cho mỗi user để chống làm kiệt quệ DB.
  + Tiếp nhận Telemetry (`telemetry`): Tối đa 60 lô/phút/IP để ngăn ngừa các cuộc tấn công từ chối dịch vụ (DoS) vào bảng log DB.
- Bảo vệ dữ liệu cá nhân (PII Redaction): Tự động quét và loại bỏ các chuỗi nhạy cảm (JWT, Token, Email, UUID, số dài) ở cả 2 đầu Client và Server.
- Ràng buộc kiểu chặt chẽ (Exhaustive Type Checking): Sử dụng cú pháp `satisfies Record<Game, GameInspector>` buộc trình biên dịch TypeScript cảnh báo ngay lập tức nếu có trò chơi mới mà chưa viết bộ kiểm tra anti-cheat.

Tính năng Xác thực & Hồ sơ người dùng (Auth & Profile) quản lý toàn bộ vòng đời tài khoản và dữ liệu hồ sơ người chơi trong hệ thống MindGem.

Các chức năng chính bao gồm:
- Chế độ Khách (Guest mode): Tài khoản khách là tài khoản Supabase `auth.users` thực sự với mật khẩu được tạo ngẫu nhiên. Việc tạo tài khoản khách được thực hiện thông qua Edge Function `/server/signup` với cờ `isGuest` và yêu cầu xác thực Cloudflare Turnstile để chống bot spam. Mọi tính toán điểm và XP đều được Server xử lý y hệt người dùng thật.
- Đăng ký (Sign up): Đăng ký tài khoản bằng Username + Password thông qua cơ chế Email-Spoofing (@mindgem.local). Không yêu cầu người dùng cung cấp email thật.

- Tải lên & Xóa Avatar: Quản lý ảnh đại diện lưu trữ tại Supabase Storage bucket 'avatars'.
- Đổi mật khẩu (Change Password): Tái xác thực với mật khẩu hiện tại trước khi cập nhật mật khẩu mới.
- Xóa tài khoản (Delete Account): Xóa vĩnh viễn tài khoản bao gồm bản ghi auth.users, hồ sơ public.profiles và toàn bộ ảnh đại diện trên storage.

4. CHI TIẾT TRIỂN KHAI (IMPLEMENTATION DETAILS)
--------------------------------------------------------------------------------

A. CHẾ ĐỘ GUEST (GUEST MODE) - SERVER-SIDE PROVISIONING
- Quy trình tạo: Client gọi Edge Function `/server/signup` kèm cờ `isGuest` và mã token từ Cloudflare Turnstile.
- Cấp phát: Server gọi `adminClient.auth.admin.createUser` tạo một tài khoản Supabase Auth thực sự (email giả định do server tự sinh, mật khẩu UUID an toàn).
- Hồ sơ: Tài khoản nhận `role = 'guest'` trong bảng `public.profiles`. Server gửi trả mật khẩu ngẫu nhiên này về để client tự động đăng nhập.
- Phiên làm việc: Khách nhận được JWT session token tiêu chuẩn. Mật khẩu không cần lưu trữ vĩnh viễn ở localStorage (dựa vào session refresh).
- Lợi ích: Tương thích 100% với hệ thống RLS (Row Level Security) của PostgreSQL mà không cần các ngoại lệ bypass dành riêng cho Guest. Bot tự động không thể spam tạo Guest rác do bị vướng Turnstile. Khi cần nâng cấp tài khoản, chỉ việc Update Email và Password thật.

B. MÔ HÌNH EMAIL-SPOOFING (@mindgem.local)
- Định nghĩa Domain & Username Regex:
  ```typescript
  export const USERNAME_RE = /^[a-z0-9_.-]{3,20}$/i;
  export const AUTH_EMAIL_DOMAIN = "mindgem.local";
  export const LEGACY_AUTH_EMAIL_DOMAINS = ["neurobics.local"] as const;
  ```
- Chuyển đổi Username -> Candidate Emails:
  ```typescript
  function authEmailCandidates(username: string): string[] {
    const name = assertValidUsername(username);
    return [AUTH_EMAIL_DOMAIN, ...LEGACY_AUTH_EMAIL_DOMAINS].map((d) => `${name}@${d}`);
  }
  ```
- Luồng Đăng nhập (`handleLogin`):
  Thử đăng nhập bằng `signInWithPassword` lần lượt qua từng email candidate (`username@mindgem.local` trước, `username@neurobics.local` sau). Nếu thành công trả về `access_token`.
- Luồng Đăng ký trên Server (`routes/auth.ts`):
  Tự động sinh email `${normalized_username}@mindgem.local` và truyền `email_confirm: true` khi gọi `adminClient.auth.admin.createUser` để xác nhận tài khoản ngay lập tức mà không cần gửi mail xác thực.

C. TURNSTILE CAPTCHA
- Client Widget (`TurnstileWidget` trong `auth-screen.tsx`):
  Render widget Cloudflare Turnstile, nhận `captchaToken` và truyền lên server khi gửi form Signup.
- Server Verification (`security.ts`):
  ```typescript
  export async function verifyTurnstile(token: string, ip: string): Promise<TurnstileVerdict> {
    const secret = Deno.env.get("TURNSTILE_SECRET_KEY");
    const body = new URLSearchParams({ secret, response: token });
    if (ip !== "unknown") body.set("remoteip", ip);
    const response = await fetch("https://challenges.cloudflare.com/turnstile/v0/siteverify", {
      method: "POST",
      body,
    });
    const result = await response.json();
    return { ok: result.success === true, codes: result["error-codes"] ?? [] };
  }
  ```
- Trả lỗi thân thiện: Hàm `turnstileMessage(codes)` dịch các mã lỗi của Cloudflare (như `timeout-or-duplicate`, `invalid-input-response`) thành thông điệp tiếng Anh rõ ràng cho người dùng.

D. RATE LIMITING & CHỐNG LẠM DỤNG
- Trích xuất IP an toàn (`clientIp` trong `security.ts`):
  ```typescript
  export function clientIp(c: Context): string {
    const forwarded = c.req.header("x-forwarded-for")?.split(",")[0]?.trim();
    return forwarded && forwarded.length > 0 ? forwarded : "unknown";
  }
  ```
  Chỉ tin tưởng phần tử đầu tiên của `x-forwarded-for` do hạ tầng Supabase Edge Function tự gắn vào, không dùng `cf-connecting-ip` hay `x-real-ip` vì client có thể tự chế header này để bypass rate limit.
- IP Hashing & Consuming Limit:
  Tạo IP hash bằng SHA-256 từ chuỗi `mindgem-signup:${ip}`.
  Gọi RPC Postgres nguyên tử `consumeRateLimit(ipHash, SIGNUP_LIMIT, SIGNUP_WINDOW_SECONDS)` với `SIGNUP_LIMIT = 10` và `SIGNUP_WINDOW_SECONDS = 900` (15 phút).

E. PROFILE CACHING & INACTIVITY DECAY
- Caching Client (`use-app-state.ts`):
  - Key local storage: `neurobics.cached_profile`.
  - Cấu trúc lưu trữ: `{ userId: p.id, profile: p, at: new Date().toISOString() }`.
  - TTL: 7 ngày (`CACHE_TTL_MS = 7 * 24 * 3600_000`).
  - Khi khởi động app hoặc gặp lỗi mạng, nếu tìm thấy cache có `cached.userId === userId` và chưa hết TTL thì dùng cache này.
  - Profile Sanitize & Hydration / Decay (`internal.ts`):
    - `sanitizeProfile(p)`: Chuẩn hóa các chỉ số 5 trục (Spatial, Logic, Memory, Speed, Focus) về khoảng `[0, 1000]`.
    - `hydrateProfile(p)`: Xử lý hiển thị chỉ số đã decay trên UI dựa trên dữ liệu đã tính toán từ phía Server.

F. QUẢN LÝ AVATAR (AVATAR UPLOAD & REMOVE)
- Hằng số giới hạn (`internal.ts`):
  `AVATAR_MAX_BYTES = 2 * 1024 * 1024` (2MB).
  `AVATAR_MIME = new Set(["image/jpeg", "image/png", "image/webp", "image/gif"])`.
- Tải ảnh đại diện (`uploadAvatar` trong `profile.ts`):
  1. Kiểm tra định dạng MIME và dung lượng file (`<= 2MB`).
  2. Xác định đường dẫn file: `${userId}/avatar.${ext}`.
  3. Dọn dẹp file cũ: Liệt kê các file trong thư mục `${userId}/` trên bucket `avatars` và xóa những file không cùng phần mở rộng (ví dụ xóa `avatar.jpg` nếu tải lên `avatar.png`).
  4. Thực hiện `storage.from("avatars").upload(path, file, { upsert: true, contentType: file.type, cacheControl: "3600" })`.
  5. Lấy public URL và gắn mốc thời gian `?t=${Date.now()}` để phá CDN/browser cache.
  6. Cập nhật `avatar_url` trong bảng `profiles`.
- Xóa ảnh đại diện (`removeAvatar` trong `profile.ts`):
  Liệt kê toàn bộ file trong `${userId}/`, xóa khỏi bucket `avatars`, và set `avatar_url = null` trong bảng `profiles`.

G. NĂM SINH (BIRTH YEAR)
- Hàm `saveBirthYear(birthYear)` trong `profile.ts` cập nhật cột `birth_year` trong bảng `profiles` thông qua Supabase RLS.
- Trong `use-app-state.ts`, hàm `submitBirthYear()` validate năm sinh nằm trong khoảng từ `1900` đến `năm hiện tại - 13`. Năm sinh là mốc quan trọng để tính toán Tuổi Não (Brain Age).

H. ĐỔI MẬT KHẨU (CHANGE PASSWORD)
- Hàm `changePassword(currentPassword, newPassword)` trong `profile.ts`:
  1. Kiểm tra `newPassword.length >= 8` và `newPassword !== currentPassword`.
  2. Gọi `getSupabase().auth.getUser()` lấy email hiện tại.
  3. Tái xác thực người dùng bằng `signInWithPassword({ email: user.email, password: currentPassword })`. Nếu thất bại, ném lỗi "Current password is incorrect."
  4. Sau khi tái xác thực thành công, cập nhật mật khẩu mới qua `getSupabase().auth.updateUser({ password: newPassword })`.

I. XÓA TÀI KHOẢN (ACCOUNT DELETION)
- Hàm `deleteActiveUserAccount()` trong `profile.ts` gửi POST request tới `/server/delete-account`.
- Xử lý tại Edge Function (`routes/account.ts`):
  1. Xác thực Bearer Token để lấy `user.id`.
  2. Dọn dẹp Storage: Liệt kê và xóa toàn bộ file trong `avatars/${userId}/`.
  3. Xóa Auth User: Gọi `adminClient.auth.admin.deleteUser(userId)` bằng Service Role Key. Thao tác này sẽ tự động xóa hàng trong `public.profiles` nhờ cài đặt `ON DELETE CASCADE`.
  4. Fallback Idempotent: Gọi thêm `adminClient.from("profiles").delete().eq("id", userId)` phòng trường hợp cơ sở dữ liệu cũ chưa có khóa ngoại CASCADE.
- Xử lý phía Client:
  Sau khi server trả về thành công, client gọi `auth.signOut()` và chủ động xóa toàn bộ key lưu trữ phiên làm việc `sb-*` trong `localStorage`.

6. BẢO MẬT & VALIDATION (SECURITY & VALIDATION)
--------------------------------------------------------------------------------
1. Cô lập Service Role Key:
   `EDGE_SERVICE_ROLE_KEY` chỉ tồn tại trên Deno Edge Runtime server. Client hoàn toàn không biết key này. Mọi thao tác quản trị đặc quyền (`createUser`, `deleteUser`) đều phải thông qua Edge Function API.
2. Bảo vệ thông tin cá nhân (PII Privacy):
   Sử dụng kỹ thuật Email-Spoofing (`username@mindgem.local`) giúp người chơi không cần cung cấp Email thật. Hệ thống chỉ thu thập thông tin cơ bản như `birth_year` (để kiểm duyệt tuổi ≥13) và `fingerprint` phục vụ chống gian lận. Khi xoá tài khoản, dữ liệu `admin_audit` vẫn được giữ 365 ngày và `cheat_flags` giữ 90 ngày (cả hai có chứa `user_id`) cho mục đích bảo mật, sau đó mới bị xoá.
3. Chống Bot / Auto Signup bằng Captcha:
   Bắt buộc xác thực Cloudflare Turnstile Token ở tầng server trước khi tiến hành tạo tài khoản. Token chỉ dùng được 1 lần và kiểm tra IP tương ứng.
4. Chống Tấn công Flood / Brute-force:
   Sử dụng IP Hash (SHA-256) và RPC `consumeRateLimit` khoá 10 lượt đăng ký trong 15 phút cho mỗi địa chỉ IP. Trích xuất IP chuẩn xác qua `x-forwarded-for`.
5. Validation Username & Password:
   - Regex: `^[a-z0-9_.-]{3,20}$` (Chỉ chấp nhận chữ thường, số, dấu gạch dưới, gạch ngang, chấm. Từ 3-20 ký tự). Chặn hoàn toàn khoảng trắng, ký tự đặc biệt, unicode và ký tự `@`.
   - Password tối thiểu 8 ký tự.
6. Row Level Security (RLS) trên DB:
   Bảng `public.profiles` áp dụng RLS: Kẻ gian không thể dùng client key sửa đổi điểm số hay thông tin của người dùng khác (`auth.uid() = id`).
7. An toàn Storage Bucket:
   Giới hạn dung lượng file avatar `<= 2MB` và kiểm tra nghiêm ngặt danh sách MIME types được phép.


7. RESOLVED RISKS (ĐÃ KHẮC PHỤC)
--------------------------------------------------------------------------------
(Tổng hợp từ tài liệu đánh giá kiến trúc `ai_review.md` liên quan đến Auth & Profile)

1. [P0] Đ5 - Cache Profile dùng chung 1 key duy nhất trong LocalStorage:

4.2. THANG ĐIỂM VÀ TÍNH ĐIỂM ELO / RATING (EMA MODEL)
- Thang điểm chuẩn: `RATING_MIN = 0`, `RATING_MAX = 1000`.
  - Chữa lành dữ liệu cũ (Auto-heal): `sanitizeRating(val)`
    + `val < 0` hoặc không phải số -> 0.
    + `val > 1000` -> kẹp xuống chính xác 1000 (đảm bảo không bao giờ reset về 0 gây mất điểm oan), đồng thời ghi lại log cảnh báo (`console.warn` / telemetry) khi việc kẹp này xảy ra để phục vụ điều tra.
- Thuật toán cập nhật EMA hai chiều (`applyRoundRating` / `pullUpRating`):
  + Nếu điểm cũ `prev <= 0` (Cold Start): Điểm ván đầu trở thành baseline ban đầu.
  + Nếu `gap = round - prev > 0` (Bứt phá): `EMA = prev + 0.4 * gap`, kẹp `max(prev + 3, EMA)`.
  + Nếu `gap < 0` (Giảm phong độ): `EMA = prev + 0.28 * gap`, kẹp `min(prev - 3, EMA)`.
  + Khoảng cách `|gap| <= 3` (`RATING_SNAP`): Nhảy thẳng về điểm ván mới để tránh tiệm cận vô hạn sat biên 999.

4.3. THIẾT KẾ CÁC TRỤC ĐỘC LẬP & CÔNG THỨC CHẤM ĐIỂM CHI TIẾT
Mỗi trục nhận tín hiệu đầu vào riêng biệt:
- Logic & Memory: HOÀN TOÀN KHÔNG CÓ THÀNH PHẦN THỜI GIAN. Người chơi nhanh không thể đẩy 5 trục lên cùng lúc nếu không suy luận đúng hoặc nhớ chính xác.
- Speed: Dựa trên MEDIAN response time (không dùng tổng thời gian hay trung bình cộng, chống nhiễu do dừng 1 nhịp).
  + Thuật toán Speed không bảo hòa (v54 non-saturating smooth exponential fill):
    * `raw = target / max(median(statRts), 1)`
    * `base = MAX * diff`
    * Nếu `raw <= 1` (chậm hơn target): `clamp(base * Math.pow(raw, 1.3))` (phạt lũy thừa 1.3).
    * Nếu `raw > 1` (nhanh hơn target): `clamp(base + (MAX - base) * (1 - exp(-ln(raw) * 1.6)) * 0.85)` (lấp đầy khoảng trống tiệm cận 0.85).
- Focus: Đo độ ổn định nhịp độ (Coefficient of Variation - CV), tỷ lệ xao nhãng (Lapse Rate), độ chính xác và phạt nếu nhịp chơi quá chậm so với target.
  + `penalty = clamp01((cv(rts) - 0.18) / (1.05 - 0.18))`
  + `pace = clamp01((4 * target - median) / (3 * target))`
  + `focus = MAX * diff * 0.92 * (1 - penalty * 0.75) * (1 - lapseRate * 1.15) * (accuracy ^ 1.15) * (pace ^ 1.25)`
- Headline Score: Trung bình cộng các trục active trong ván (`headline = sum(active_axes) / count(active_axes)`).

Chi tiết công thức từng game trên server (`round-scoring.ts`):
1. Schulte Table:
   - Input: `cells` (9, 16, 25, 36), `hitRts`, `wrongClicks`, `failed`.
   - Speed: `speed(statRts, perTarget, diff) * completion`.
   - Focus: `focus(statRts, accuracy, diff, perTarget) * completion`.
   - Spatial: Trục phụ. Lấy 1/3 mảng RT giai đoạn cuối (`late`): `clamp(MAX * 0.87 * diff * min(1, ratio(per * 1.25, median(late))) * accuracy * completion)`.
2. Sudoku:
   - Input: `difficulty` (Easy->Extreme), `placements`, `moveRts`, `mistakes`, `reEntries`, `repeatMistakes`, `actualClues`.
   - Độ khó thực tế `effectiveSudokuDiff` điều chỉnh theo `actualClues` thực tế.
   - Logic: `clamp(MAX * diff * (1 - mistakes/3)^1.35)`. Ván `failed` giảm còn 35%.
   - Memory: `retention = 1 - (reEntries + repeat*1.75) / max(3, placements*0.2)`. `clamp(MAX * diff * retention)`.
   - Speed: `speed(statRts, per, diff) * completion`.
3. Stroop Test:
   - Input: `totalStimuli`, `wrongClicks`, `rts`. `STROOP_TRIALS = 30`.
   - Speed: `speed(statRts, 1400, 0.78) * completion`.
   - Focus: `focus(statRts, accuracy, 0.78, 1400) * completion`.
4. Reaction Time:
   - Input: `rts` (8-12 mẫu), `falseStarts`.
   - `accuracy = rts.length / (rts.length + falseStarts * 2.5)`.
   - Speed: `speed(statRts, 280, 0.95)`. Target 280ms, diff 0.95.
   - Focus: `focus(statRts, accuracy, 0.88, 280)`.
5. Memory Matrix:
   - Input: `clearedLevels` / `maxLevel`, `wrongClicks`.
   - `progression = clamp01(level / 16)`.
   - `progressionFactor = PROG_FLOOR + (1 - PROG_FLOOR) * (progression ^ 0.75)` với `PROG_FLOOR = 0.24`.
   - Memory: `clamp(MAX * 0.88 * progressionFactor * accuracy)`.
   - Spatial: `clamp(MAX * 0.82 * progressionFactor * accuracy)`.
6. N-Back:
   - Input: `n` (1-6), `trials`, `hits`, `misses`, `falseAlarms`, `rts`.
   - `hitRate = hits / targets`, `faRate = falseAlarms / nonTargets`, `accuracy = hitRate - faRate * 0.95`. `depth = n / 6`.
   - Memory: `clamp(MAX * (accuracy ^ 1.2) * (0.62 + 0.36 * depth))`.
   - Focus: `clamp(MAX * (accuracy ^ 1.15) * (0.62 + 0.32 * (1 - faRate)) * (0.72 + 0.26 * depth))`.
   - Speed: `speed(rts, 620, 0.82)`.
7. Math Sprint:
   - Input: `difficulty`, `totalProblems`, `correct`, `wrong`, `rts`.
   - Logic: `clamp(MAX * diff * accuracy)`.
   - Speed: `speed(clean, target, diff) * (0.55 + 0.45 * accuracy)`.
8. Go / No-Go:
   - Input: `trials` (30-48), `goTrials`, `nogoTrials`, `hits`, `misses`, `falseAlarms`, `correctRejections`, `rts`.
   - `accuracy = clamp01(hitRate) * clamp01(1 - faRate)` (phép nhân chống chiêu trò bấm mọi ô hoặc không bấm ô nào).
   - Focus: `clamp(MAX * 0.9 * (accuracy ^ 1.15) * (0.62 + 0.38 * (1 - faRate * 1.35)))`.
   - Speed: `speed(statRts, 420, 0.88) * Math.pow(1 - faRate, 0.9)`.
9. Mental Rotation:
   - Input: `trials` (20-32), `correct`, `wrong`, `rts`, `angles`, `mirrors`, `correctFlags`.
   - `angleLoad`: Trung bình `|sin(angle/2)|` của các câu đúng. `angleFactor = 0.78 + 0.24 * meanAngleLoad`.
   - Spatial: `clamp(MAX * 0.95 * (accuracy ^ 1.15) * angleFactor)`.
   - Speed: `speed(statRts, 1400, 0.72)`.
10. Corsi Block:
    - Input: `span` (0-9), `trials`, `correctTrials`, `taps`, `wrongClicks`, `rts`.
    - `spanNorm = (span - 2) / 6`. `spanFactor = SPAN_FLOOR + (1 - SPAN_FLOOR) * (spanNorm ^ exp)`.
    - Memory: `clamp(MAX * 0.95 * spanFactor(0.65) * (0.7 + 0.3 * accuracy))`.
    - Spatial: `clamp(MAX * 0.84 * spanFactor(0.6) * ((1 - errorRate) ^ 1.2))`.
11. Trail Making:
    - Input: `nodes` (12-40), `mode` ("A" | "B"), `wrongClicks`, `rts`.
    - Target: Mode A = 760ms, Mode B = 1100ms. Diff: Mode A = 0.78, Mode B = 0.90.
    - Speed: `speed(statRts, target, diff)`.
    - Focus: `focus(statRts, accuracy, diff, target)`.
12. Visual Search:
    - Input: `totalTimeMs`, `score`, `mistakes`, `rts`.
    - Speed: `speed(statRts, 1100, 0.85)`.
    - Focus: `focus(statRts, accuracy, 0.85, 1100)`.

4.4. TÍNH CHỈ SỐ NHẬN THỨC VÀ TUỔI NÃO (COGNITIVE INDEX & BRAIN AGE)
- Chỉ số nhận thức toàn cầu (`cognitiveIndex`):
  + Từ Phase 12 (Tuần 3), `cognitive_index` được tính toán hoàn toàn trên Database (qua DB function `compute_cognitive_index` và View `friend_leaderboard`).
  + **Decay (Suy giảm)**: Trước khi tính Index, từng trục được tính `effective_rating()` dựa trên `peak_rating`. Decay bắt đầu sau 15 ngày không chơi (mỗi ngày -1%), và chạm đáy ở 35% của đỉnh phong độ.
  + **Nội suy (Interpolation)**: `compute_cognitive_index()` tính trung bình cộng 5 trục `effective_rating`. Những trục chưa từng chơi (score = 0) sẽ được nội suy (phạt 30%) dựa trên trung bình các trục đã mở.
- Tuổi não (`calcBrainAge`):
  + Yêu cầu đủ `CALIBRATION_ROUNDS = 5` ván chơi calibration.
  + Biên độ tuổi tối đa: `MAX_AGE_SWING = 12` năm.
  + Phân tầng tuổi: Hệ thống sử dụng 5 tầng tuổi riêng biệt: 13-17, 18-24, 25-34, 35-49, 50+. Percentile của user được tính so với population *của đúng tầng tuổi đó*.
  + Xử lý mẫu nhỏ (Bayesian Shrinkage): Khi một tầng tuổi chưa đủ `MIN_POPULATION (mặc định 10) * 4` (32 người), hệ thống sẽ hòa trộn (blend) phân phối của tầng đó với *phân phối toàn cục thực tế* của toàn hệ thống, thay vì dùng một hằng số cứng. (Chỉ dùng `DEFAULT_POPULATION = { mean: 380, sd: 180 }` nếu toàn bộ hệ thống chưa ai chơi).
  + Tính Percentile bằng công thức xấp xỉ hàm lỗi Abramowitz & Stegun (`erf`):
    `z = (index - mean) / sd`
    `percentile = clamp01(0.5 * (1 + erf(z / sqrt(2))))`
  + `advantage = (percentile - 0.5) * 2 * MAX_AGE_SWING`
  + `brainAge = round(clamp(realAge - advantage, 5, 120))`

4.5. HỆ THỐNG XP & LEVEL (ENGAGEMENT SYSTEM)
- XP thưởng theo ván chơi (`calculateRoundXp`):
  + `base = 15`, `perf = (score / 1000) * 45` (tối đa 60 XP/ván).
  + Hệ số mệt mỏi trong ngày (`fatigue = max(0.1, 1 - roundIndexToday * 0.15)`).
- Derive Level từ tổng XP (`levelFromXp`):
  + `completed = floor((-1 + sqrt(1 + totalXp / 12.5)) / 2)`
  + `level = completed + 1`
  + XP tích lũy yêu cầu cho level L: `xpRequiredForLevel(L) = 50 * (L - 1) * L`.
- Danh hiệu Level:
  + Level 1-4: Novice (#94A3B8)
  + Level 5-9: Explorer (#10B981)
  + Level 10-19: Thinker (#00D4FF)
  + Level 20-34: Strategist (#A855F7)
  + Level 35-49: Neural Master (#F59E0B)
  + Level >= 50: Neuro Sage (#F43F5E)

4.6. HÀNG ĐỢI VÀ ĐỒNG BỘ NGOẠI TUYẾN (OFFLINE QUEUE & SYNC)
- Khi mất kết nối mạng, hook `useRoundSubmission` tạo ticket giả dạng `offline-{game}-{timestamp}`.
- Ván chơi hoàn tất được đẩy vào hàng đợi LocalStorage `neurobics.offline_queue.[userId]` (tối đa 200 ván, cơ chế FIFO) thông qua `pushOfflineRound`.
- Mỗi ván ngoại tuyến sinh một `clientRoundId` (UUID) duy nhất.
- Khi có mạng trở lại, hook `useOfflineSync` tự động gửi lô tối đa 25 ván tới `/server/sync-offline-rounds`.
- Server đối chiếu `clientRoundId` trong bảng `round_tickets` để đảm bảo tính bất biến/tránh ghi trùng (Idempotency).

5. LUỒNG DỮ LIỆU (DATA FLOW)
--------------------------------------------------------------------------------

[BƯỚC 1: MỞ GAME & LẤY TICKET]
Người dùng click chọn game trên UI -> `useRoundSubmission.prepareRound(game)`
    - Client gọi POST /server/start-round { game }
  - Server kiểm tra Auth User & Rate limit (tối đa 20 ván/phút)
  - Server đóng vé cũ chưa nộp (nếu có) và cấp phát vé mới từ `ticket_pool` qua RPC `start_round_with_pool` (Pre-mint pool giảm cold-start - ADR-0008).
  └─ Server trả về { roundId, game, startedAt, expiresAt } (thời gian sống 3 giờ)

[BƯỚC 2: CHƠI GAME & GHI TELEMETRY]
Người dùng bắt đầu chơi (`beginPlay`) -> Lưu `performance.now()`
  └─ Trong quá trình chơi, Game Component thu thập:
     - Mảng thời gian phản ứng từng câu (`rts` / `hitRts` / `moveRts`)
     - Số lần bấm sai (`wrongClicks` / `mistakes` / `falseAlarms` / `falseStarts`)
     - Cấp độ đạt được (`maxLevel` / `clearedLevels` / `span`)
     - Tổng thời gian hoàn thành ván (`timeMs`)

[BƯỚC 3: NỘP VÁN CHƠI & CHẤM ĐIỂM SERVER]
Người dùng hoàn thành ván -> Game gọi handler nộp dữ liệu -> `submitRound(roundId, game, telemetry)`
  └─ Client gửi POST /server/submit-round { roundId, game, telemetry, fingerprint }
  └─ Server kiểm tra ticket trong DB:
     + Ticket phải tồn tại, đúng user, đúng game, chưa submitted, chưa hết hạn.
  └─ Server tính thời gian trôi qua thực tế trên Server: `serverElapsedMs = Date.now() - ticket.started_at`.
  └─ Lớp chống gian lận `inspectRound(game, telemetry, serverElapsedMs)`:
     + Nếu dính HARD FLAG -> Đốt ticket lập tức, ghi RPC `record_cheat_flag`, trả 422 `anticheat_hard`.
     + Nếu dính SOFT FLAG -> Ghi log cảnh báo qua `record_cheat_flag`, vẫn tiếp tục chấm điểm.
  └─ Lớp Validate & Scoring `scoreAndValidate(game, telemetry, serverElapsedMs)`:
     + Chạy `assertCountBounds` & `assertRtBounds` (chặn RT < 80ms hoặc RT > 60s).
     + Gọi Scorer tương ứng trong `SCORERS[game]` để tính điểm các trục.
     + Kiểm tra `scored.timeMs <= serverElapsedMs + 15000ms`.
  └─ Server thực thi RPC Postgres Transaction `submit_round_transaction`:
     + Cập nhật các cột điểm tương ứng trong `profiles` bằng công thức EMA.
     + Tăng cột session counter của game tương ứng (vd: `schulte_sessions = schulte_sessions + 1`).
     + Thêm dòng vào `training_sessions` & `xp_events`.
     + Trigger trg_xp_events_apply tự cộng xp_awarded vào profiles.total_xp.
        + Level được derive từ total_xp (levelFromXp), không lưu cột riêng.
     + Đánh dấu ticket `submitted_at = now()`.
  └─ Server trả về thông tin profile mới cập nhật + các trục điểm thu được (`axes`, `headline`, `xpAwarded`, `leveledUp`).

[BƯỚC 4: HIỂN THỊ KẾT QUẢ VÀ CẬP NHẬT UI]
Client nhận phản hồi thành công -> `useRoundSubmission` xử lý:
  └─ Cập nhật state `profile` của ứng dụng.
  └─ Tính toán hiệu số điểm tăng/giảm cho từng trục (`applyAxes`).
  └─ Hiển thị màn hình Overlay Kết quả Ván chơi (`RoundResultOverlay`).
  └─ Tăng `gamificationKey` để kích hoạt hiệu ứng chúc mừng (Confetti / Level up animation).

6. BẢO MẬT & VALIDATION (SECURITY & VALIDATION)
--------------------------------------------------------------------------------
1. Ranh giới Server-Client (Server-Only Scoring):
   - Mọi thuật toán chấm điểm và quy tắc tính EMA thực sự nằm duy nhất tại `supabase/functions/_shared/round-scoring.ts`. Client chỉ giữ kiểu dữ liệu DTO và hàm tính preview tạm thời.
2. Xác thực Vé Ván chơi (Ticket-based Lifecycle):
   - Người dùng không thể gửi trực tiếp điểm số vào DB. Mọi ván chơi phải có `roundId` gắn với 1 vé hợp lệ sinh ra từ server trước thời điểm chơi.
   - Mỗi người dùng chỉ có 1 vé active tại một thời điểm (vé cũ tự đóng khi mint vé mới).
   - Khống chế tốc độ tạo vé: Tối đa 20 vé/phút (`MAX_TICKET_STARTS_PER_MINUTE`).
3. Kiểm tra Ràng buộc Thời gian & Dữ liệu Vật lý:
   - `serverElapsedMs` do server tự đo dựa trên thời gian tạo vé. Dữ liệu client khai báo không thể vượt quá `serverElapsedMs + 15s`.
   - Ngưỡng thời gian phản ứng con người (`HARD_MIN_RT_MS = 80ms`): Bất kỳ lượt bấm nào dưới 80ms đều bị coi là vi phạm giới hạn sinh học con người.
   - Giới hạn số lượng phần tử (`rts.length <= 5000`) chống tấn công từ chối dịch vụ (DoS) bằng payload khổng lồ.
   - Kiểm tra tính nhất quán logic (`assertCountBounds`): `correct + wrong == trials`, `hits + misses == goTrials`, `falseAlarms <= nogoTrials`...
4. Tầng Chống Gian Lận Đa Cấp (Anti-cheat Inspection):
   - Hard Flags: Huỷ ván ngay lập tức và đốt vé (burn ticket) trước khi trả về HTTP 422 để ngăn kẻ gian dùng API làm Oracle dò ngưỡng.
   - Soft Flags: Ghi vết gian lận nghi vấn vào cơ sở dữ liệu (`cheat_flags`) để phân tích hành vi mà không ảnh hưởng trực tiếp đến trải nghiệm người chơi bình thường.
   - Liên kết dấu vân tay thiết bị (`link_device`) lưu tối đa 200 ký tự fingerprint để phát hiện bot/multi-account.

1. TỔNG QUAN (OVERVIEW)
----------------------------------------------------------------------------------------------------
Phân hệ Gamification & Social trong dự án MindGem là hệ thống cốt lõi nhằm thúc đẩy động lực luyện tập hàng ngày (user engagement & retention), theo dõi Chỉ số Nhận thức (Cognitive Index - CI), vinh danh thành tựu cá nhân và kết nối cộng đồng người chơi.

Phân hệ bao gồm 4 trụ cột chức năng chính:
- Thành tựu (Achievements / Badges): Hệ thống 52+ huy hiệu danh hiệu được chia thành 5 hạng (Đồng, Bạc, Vàng, Bạch kim, Kim cương) và 6 nhóm mục tiêu. Người chơi mở khoá danh hiệu thông qua việc tích luỹ số ván, nâng cao cấp độ, chinh phục các chỉ số nhận thức và vượt qua thử thách riêng của từng trò chơi. Phần thưởng XP tương ứng được hệ thống tự động cộng vào tài khoản.
- Nhiệm vụ (Daily & Weekly Quests): Hệ thống gồm 3 nhiệm vụ ngày (làm mới lúc 00:00 GMT+7) và 3 nhiệm vụ tuần (làm mới vào thứ Hai GMT+7). Tiến độ nhiệm vụ được tính toán tự động dựa trên kết quả luyện tập thực tế. Người chơi chủ động bấm nút "NHẬN" (Claim) trên giao diện để thu thập điểm kinh nghiệm (XP).
- Xã hội & Bảng xếp hạng Bạn bè (Social & Friends Leaderboard): Cho phép tìm kiếm người chơi khác theo tên tài khoản (tối thiểu 2 ký tự), gửi/chấp nhận/từ chối lời mời kết bạn, huỷ kết bạn và theo dõi Bảng xếp hạng riêng (Private Leaderboard) để so kè Chỉ số Nhận thức (CI) và Tổng XP tích luỹ với danh sách bạn bè đã kết nối.
- Lịch sử Luyện tập & Tiến trình (Training History & Progress Chart): Ghi nhận chi tiết từng ván đấu (thời gian, điểm số, 5 trục nhận thức Speed, Focus, Spatial, Logic, Memory, XP thưởng), quản lý Kỷ lục cá nhân (Personal Bests) theo từng trò chơi (đặc biệt hỗ trợ kỷ lục phân mảnh theo cấu hình ma trận và chế độ chơi cho Schulte Grid), cùng biểu đồ tiến trình 7/30/90 ngày trực quan với tính năng hỗ trợ người mù màu.

A. Danh mục Thành tựu & Phân hạng (Achievements Catalog):

B. Chuỗi Phân giải Nhãn Nhiệm vụ (Quest Labeling Resolution Chain):
Để đảm bảo giao diện KHÔNG BAO GIỜ hiển thị mã kỹ thuật thô (như `w_games_7` hay `q_rounds_3`), hàm `resolveQuestLabel(code, lang, serverTitle)` thực hiện phân giải theo 4 cấp ưu tiên nghiêm ngặt:
  1. Ưu tiên 1: `serverTitle` trả về từ database RPC (nếu có và khác chuỗi mã `code`).
  2. Ưu tiên 2: Ánh xạ cứng từ từ điển `QUEST_LABELS[code][lang]`.
  3. Ưu tiên 3: Hàm `humanizeQuestCode(code, lang)` tự động phân tích cấu trúc mã dạng snake_case:
     - `rounds_N` -> "Chơi N ván" / "Play N rounds"
     - `score_N` -> "Đạt N+ trong một ván" / "Score N+ in one round"
     - `score_N_M` -> "Đạt N+ trong M ván" / "Score N+ in M rounds"
     - `games_N` -> "Chơi N trò khác nhau" / "Play N different games"
     - `play_<game>_N` -> "Chơi <Tên trò> N ván" / "Play N <Tên trò> rounds" (tra cứu qua `QUEST_GAME_NAMES`)
     - Tiền tố `w_` -> Thêm nhãn "Tuần: " / "Weekly: "
  4. Ưu tiên 4: Fallback chuỗi an toàn "Nhiệm vụ" (tiếng Việt) hoặc "Quest" (tiếng Anh).

Nhờ đó, người dùng vẫn phân biệt được các đường biểu diễn khi in đen trắng hoặc khi không nhìn rõ màu sắc.


5. LUỒNG DỮ LIỆU (DATA FLOW)
----------------------------------------------------------------------------------------------------
A. Luồng Mở khoá Thành tựu & Đọc Tiến độ:
  1. Người dùng chuyển sang tab Thành tựu -> `AchievementsPanel` được mount.
  2. `useEffect` kích hoạt `syncAchievements()` gửi yêu cầu RPC `sync_achievements` tới Supabase.
  3. Database chạy Stored Procedure quét bảng `training_sessions` và `profiles` của người dùng:
     - Kiểm tra điều kiện từng thành tựu chưa mở.
     - Nếu đủ điều kiện, ghi nhận bản ghi mở khoá vào bảng `user_achievements`, và ghi 1 giao dịch thưởng XP vào bảng `xp_events` (DB Trigger sẽ tự cộng vào `profiles.total_xp`).
     - Trả về danh sách các huy hiệu kèm thuộc tính `newly_unlocked`.
  4. Nếu có huy hiệu `newly_unlocked === true`, client phát hiệu ứng Toast "Mở khoá thành tựu mới!".
  5. Tiếp theo, client gọi `fetchAchievementProgress()` -> RPC `get_achievement_progress` trả về mảng `AchievementProgress[]` chứa tỷ lệ `progress / goal`.
  6. Component tính toán tổng XP đã đạt, số lượng huy hiệu đã mở, sắp xếp danh sách huy hiệu và render ra màn hình.

B. Luồng Làm Nhiệm vụ & Nhận thưởng XP:
  1. Người dùng hoàn thành một ván luyện tập -> Hệ thống lưu ván vào `training_sessions`.
  2. Người dùng mở tab Nhiệm vụ -> `QuestsPanel` gọi `fetchDailyQuests()` -> RPC `get_daily_quests`.
  3. Database tổng hợp số ván đấu, điểm số đạt được trong ngày (tính từ 00:00 giờ Việt Nam) và trong tuần (tính từ 00:00 thứ Hai giờ Việt Nam), so sánh với các mốc nhiệm vụ và trả về danh sách `DailyQuest[]`.
  4. Nếu một nhiệm vụ có `progress >= goal` và `claimed === false`, nút "NHẬN" (Claim) sáng lên.
  5. Người dùng nhấn "NHẬN" -> Client gọi `claimQuest(code)` -> RPC `claim_quest(p_code)`.
  6. Database kiểm tra nguyên tử: khẳng định nhiệm vụ đã đạt và chưa từng nhận thưởng -> đặt `claimed = true` trong bảng `user_quests` -> ghi nhận một giao dịch vào bảng `xp_events` (Mô hình Ledger) -> DB Trigger `trg_xp_events_apply` sẽ tự động cộng thêm `xp_awarded` vào `profiles.total_xp` mà không cần query cập nhật trực tiếp -> trả về số XP thưởng.
  7. Client nhận kết quả, hiển thị Toast "Đã nhận +X XP", làm mới lại danh sách nhiệm vụ và phát sự kiện `onClaimed` để cập nhật tổng XP trên thanh Header.

C. Luồng Tìm kiếm người chơi & Kết bạn:
  1. Người dùng nhập tên tài khoản cần tìm vào ô Search trong `FriendsPanel`.
  2. `useEffect` sử dụng timer hoãn (debounce 350ms, rate limit DB-level 15 req/5 phút). Khi từ khóa `query.trim().length >= 2`, hàm `searchPlayers(query)` được gọi -> RPC `search_players`.
  3. Database trả về tối đa 10 kết quả phù hợp (`PlayerSearchResult[]`).
  4. Người dùng nhấn nút "Kết bạn" bên cạnh tên người chơi -> Gọi `sendFriendRequest(targetId)` -> RPC `send_friend_request`.
  5. Database chèn bản ghi mới vào bảng `friendships` với `status = 'pending'`.
  6. Client hiển thị Toast "Đã gửi lời mời", xóa từ khóa tìm kiếm và gọi lại `load()` (`fetchFriends()` & `fetchFriendLeaderboard()`) để cập nhật giao diện.


6. BẢO MẬT & VALIDATION (SECURITY & VALIDATION)
----------------------------------------------------------------------------------------------------
A. Nguyên tắc Chống Gian lận XP & Thành tựu (Server-Enforced Integrity):
- Toàn bộ điều kiện hoàn thành nhiệm vụ và mở khoá thành tựu được kiểm tra trực tiếp từ các ván đấu hợp lệ lưu trên server (`training_sessions`). Các ván đấu này bắt buộc phải trải qua quy trình anti-cheat (`scoreAndValidate`, `inspectRound`) ở Edge Function trước khi được ghi vào cơ sở dữ liệu.
- Phía Client không gửi bất kỳ tham số cờ hoàn thành nào lên server. RPC `claim_quest` và `sync_achievements` tự động xác minh tính hợp lệ và chỉ cộng XP một lần duy nhất (Idempotent).

B. Bảo mật Context & Quyền truy cập (Supabase RLS & Security Definer):
- Tất cả các hàm RPC liên quan đến Gamification và Social đều sử dụng `SECURITY DEFINER` và tự động trích xuất `auth.uid()` từ JWT Token do Supabase Auth quản lý. Người dùng không thể truyền `user_id` giả mạo để nhận thưởng hộ tài khoản khác.
- Các thao tác xã hội (`respondFriendRequest`, `removeFriend`) kiểm tra nghiêm ngặt quyền sở hữu: chỉ có người nhận mới có quyền chấp nhận/từ chối lời mời (`friendship_id`), và chỉ có hai người trong cuộc mới có quyền hủy kết bạn.
- Bảng xếp hạng bạn bè (`get_friend_leaderboard`) áp dụng INNER JOIN bắt buộc kiểm tra `status = 'accepted'`, đảm bảo không rò rỉ Chỉ số Nhận thức (CI) cho người lạ.

C. Validation & Giới hạn Tải (Rate Limiting & Input Sanitization):
- Tìm kiếm người chơi (`searchPlayers`): Bắt buộc từ khóa tìm kiếm tối thiểu 2 ký tự (`query.trim().length >= 2`), ép kiểu và cắt khoảng trắng, giới hạn tối đa 10 kết quả (`p_limit: 10`), kết hợp hoãn gõ (debounce 350ms, rate limit DB-level 15 req/5 phút) phía UI để ngăn chặn tấn công Spam RPC Request.
- Phân trang Lịch sử (`fetchTrainingHistory`): Giới hạn tham số `limit` trong khoảng an toàn `[1, 200]` (`Math.min(Math.max(opts.limit ?? 50, 1), 200)`), phòng tránh việc truy vấn hàng ngàn dòng dữ liệu gây cạn kiệt bộ nhớ trình duyệt.

1. TỔNG QUAN (OVERVIEW)
-------------------------------------------------------------------------------
Tính năng Offline & Progressive Web App (PWA) trong hệ thống MindGem cung cấp trải nghiệm liền mạch cho người dùng ngay cả khi không có kết nối Internet hoặc khi kết nối mạng chập chờn. 

Mục tiêu chính của hệ thống bao gồm:
- PWA Support: Khả năng cài đặt ứng dụng trực tiếp lên thiết bị (Desktop, Android, iOS) với giao diện độc lập (display: standalone), hỗ trợ biểu tượng tùy chỉnh (maskable icons), phối màu giao diện mượt mà (#050914) và bộ lắng nghe sự kiện cài đặt chuẩn hóa.
- Offline Playing (Chế độ chơi ngoại tuyến): Cho phép người dùng tiếp tục chơi các trò chơi rèn luyện trí nhận thức khi không có mạng. Các ván đấu được tạm lưu ở bộ nhớ local và tự động tính điểm / XP tạm thời để hiển thị kết quả ngay tức thì.
- Guest Mode (Chế độ chơi thử dành cho Khách): Người dùng mới có thể trải nghiệm toàn bộ các game mà không cần đăng ký tài khoản. Điểm số và tiến trình được đồng bộ lên máy chủ y hệt người dùng đã đăng ký (ADR-0007).
- Offline Queue & Auto Sync: Lưu giữ các ván chơi chưa đồng bộ trong LocalStorage (`neurobics.offline_queue.[userId]`) theo cơ chế FIFO (tối đa 200 ván). Khi thiết bị có mạng trở lại, hệ thống sẽ tự động kích hoạt tiến trình đồng bộ theo từng batch (tối đa 25 ván/batch) lên Supabase Edge Functions server.

B. CÁC HẰNG SỐ QUAN TRỌNG
- `OFFLINE_QUEUE_KEY`: `"neurobics.offline_queue.[userId]"` - Key lưu trữ hàng đợi trong LocalStorage.
- `MAX_QUEUE`: `200` - Số lượng ván đấu tối đa lưu giữ trong hàng đợi local (FIFO).
- `MAX_SYNC_BATCH`: `25` - Số ván tối đa gửi lên server trong 1 HTTP request đồng bộ.
- `MAX_OFFLINE_AGE_MS`: `7 * 24 * 3600_000` (7 ngày) - Tuổi thọ tối đa của ván offline được server chấp nhận.
- `MAX_TICKET_STARTS_PER_MINUTE`: `20` - Hạn ngạch tạo ticket khởi tạo ván / phút / user trên server.

C. THUẬT TOÁN & LOGIC XỬ LÝ CHI TIẾT

1. Hàng đợi Offline & Quản lý Bộ nhớ (`offline-queue.ts`):
   - Khi ghi ván mới (`pushOfflineRound`):
     ```typescript
     const queue = getOfflineQueue();
     if (queue.length >= MAX_QUEUE) {
       queue.shift(); // Thuật toán FIFO: loại bỏ ván cũ nhất khi đạt ngưỡng 200
     }
     queue.push({
       ...round,
       clientRoundId: crypto.randomUUID(),
       schemaVersion: 1,
       createdAt: new Date().toISOString(),
     });
     writeOfflineQueue(queue); // Ghi vào localStorage & dispatch event "offline-queue-updated"
     ```
   - Chống Race Condition khi đồng bộ (`syncOfflineQueue`):
     Để tránh mất các ván người dùng vừa hoàn thành trong lúc request API `syncEndpoint` đang chờ (await), hàm sẽ đọc lại hàng đợi tươi (`freshQueue = getOfflineQueue()`) trước khi tiến hành lọc bỏ các ván đã chốt (`settledIds` chứa trạng thái `ok`, `duplicate`, `rejected`):
     ```typescript
     const freshQueue = getOfflineQueue();
     const newQueue = freshQueue.filter((item) => !settledIds.has(item.clientRoundId));
     writeOfflineQueue(newQueue);
     ```

2. Tự động Đồng bộ Ngoại tuyến (`use-offline-sync.ts`):
   - Hook lắng nghe 2 sự kiện: `window.addEventListener("online", handleOnline)` và `window.addEventListener("offline-queue-updated", onQueueUpdated)`.
   - Sử dụng `syncingRef = useRef(false)` làm cờ khóa (Mutex) chống việc kích hoạt nhiều tiến trình đồng bộ song song khi có nhiều sự kiện phát ra liên tiếp.
   - Khi đồng bộ thành công, kích hoạt sự kiện toàn cục `window.dispatchEvent(new Event("offline-sync-complete"))`.

3. Cài đặt PWA & Kiểm tra Môi trường (`use-pwa-install.ts`):
   - Sử dụng pattern React 18 `useSyncExternalStore` để đăng ký lắng nghe sự kiện mà không bị tearing trong chế độ Concurrent Rendering.
   - Nhận diện môi trường iOS:
     ```typescript
     function detectIos(): boolean {
       if (typeof navigator === "undefined") return false;
       return (
         /iPad|iPhone|iPod/i.test(navigator.userAgent) ||
         (navigator.platform === "MacIntel" && navigator.maxTouchPoints > 1)
       );
     }
     ```
   - Nhận diện chế độ Standalone (Đã cài đặt):
     ```typescript
     function detectStandalone(): boolean {
       if (typeof window === "undefined") return false;
       const iosStandalone = (navigator as Navigator & { standalone?: boolean }).standalone;
       return Boolean(iosStandalone || window.matchMedia("(display-mode: standalone)").matches);
     }
     ```

4. Luồng Chơi & Dự phòng Ngoại tuyến (`use-round-submission.ts`):
   - Khi chọn Game: Gọi `prepareRound(game)`. 
     
     + Gọi API `startRound(game)` để lấy ticket thật từ server.
     + Nếu Mất mạng (`isNetworkErrorLike(err)`): Tự động cấp ticket dự phòng `offline-{game}-{now}`.
   - Khi Hoàn thành Ván (`completeRound`):
     
     + Nếu ticket là `"offline-"` hoặc lệnh `submitRound` ném lỗi mạng (`isNetworkErrorLike`):
       Gọi `pushOfflineRound(...)` để đẩy vào queue local, đồng thời tính điểm tạm thời bằng `estimateRoundResult` để cập nhật UI ngay cho người chơi.

5. Chấm điểm Cục bộ (`estimateRoundResult`):
   - Khách (Guest) được xử lý y hệt người dùng thật thông qua cơ chế Server Auth. Tất cả ván chơi đều được gửi lên máy chủ hoặc offline queue.
   - Sử dụng một module riêng trên client (UI-only) để tính điểm tạm thời (provisional). Kết quả này được hiển thị dưới dạng "Pending Sync" và không làm thay đổi bảng xếp hạng hay Brain Age cho đến khi được server xác nhận. Tuyệt đối không import các logic chống gian lận hay `scoreAndValidate` từ server (để tránh rò rỉ ngưỡng anti-cheat).

6. Xử lý Đồng bộ ở Server (`supabase/functions/server/routes/rounds.ts`):
   - Endpoint `POST /server/sync-offline-rounds` nhận mảng `rounds` (tối đa 25 ván).
   - Kiểm tra thời gian khởi tạo ván `startedAt`: Từ chối nếu `startedAt` lớn hơn thời gian hiện tại > 60s hoặc cũ hơn 7 ngày (`MAX_OFFLINE_AGE_MS`).
   - Kiểm tra Idempotency: Tra cứu DB `round_tickets` xem đã có ticket nào chứa `client_round_id` này và đã `submitted_at` chưa. Nếu rồi -> Trả về status `"duplicate"`.
   - Tạo Ticket Thật: Nếu chưa có ticket, insert một bản ghi ticket thật vào DB `round_tickets` với `client_round_id`.
   - Kiểm tra Anti-cheat (`inspectRound`): Bổ sung Soft Flag đặc thù: `"Offline sync: timing verification bypassed"`. Nếu phát hiện Hard Flag gian lận -> Đốt ticket (`submitted_at = now`) và trả về status `"rejected"` với code `"anticheat_hard"`.
   - Ghi nhận giao dịch DB (`submit_round_transaction`): Cập nhật Rating trục, XP, và lịch sử ván chơi nguyên tử (Atomic Transaction) qua RPC Supabase.

6. BẢO MẬT & VALIDATION (SECURITY & VALIDATION)
-------------------------------------------------------------------------------
1. Chống Spam & DoS Server:
   - Client Queue Cap: Giới hạn tối đa 200 ván trong LocalStorage (`MAX_QUEUE = 200`). Sử dụng cơ chế FIFO đẩy ván cũ nhất ra ngoài khi đầy.
   - Server Batch Limit: Giới hạn tối đa 25 ván cho mỗi lượt request đồng bộ (`MAX_SYNC_BATCH = 25`). Nếu gửi > 25 ván, server lập tức từ chối với HTTP 413 (Payload Too Large).
   - Server Ticket Rate Limit: Tối đa 20 lượt khởi tạo ticket (`start-round`) trong vòng 1 phút cho mỗi người dùng (`MAX_TICKET_STARTS_PER_MINUTE = 20`).

2. Ràng buộc Thời gian & Tính Hợp lệ của Ván Offline:
   - Server kiểm tra `startedAt`: Từ chối ván nếu thời gian bắt đầu nằm ở tương lai (> 60s so với server clock) hoặc vượt quá 7 ngày tuổi (`MAX_OFFLINE_AGE_MS = 7 * 24 * 3600_000`).
   - Server kẹp giới hạn `clientElapsedMs`: Không tin tưởng tuyệt đối con số client gửi lên. Giá trị `elapsed` bắt buộc nằm trong khoảng `[500ms, 2 giờ]`:
     `const elapsed = Math.min(Math.max(Number(clientElapsedMs) || 0, 500), 2 * 3600_000);`

3. Idempotency & Chống Replay Attack:
   - Mỗi ván offline khi tạo ở client được gán một `clientRoundId` ngẫu nhiên chuẩn UUIDv4 (`crypto.randomUUID()`).
   - Server lưu `client_round_id` vào bảng `round_tickets`. Trước khi xử lý, server tra cứu `client_round_id` để phát hiện ván đã được nộp trước đó. Nếu đã chốt, trả về status `"duplicate"` mà không cộng điểm lần hai.

4. Anti-Cheat & Ghi nhận Dấu vết Gian lận:
   - Mặc dù ván offline không có `serverElapsedMs` chính xác từ ticket thời gian thực, server vẫn chạy toàn bộ bộ kiểm tra Anti-cheat `inspectRound(gameId, telemetry, elapsed)`.
   - Tự động chèn Soft Flag: `"Offline sync: timing verification bypassed"` để phân biệt ván đấu ngoại tuyến với ván đấu trực tuyến.
   - Nếu vi phạm Hard Flag (như gian lận phản xạ siêu nhiên, dữ liệu telemetry vô lý): Ticket bị hủy ngay lập tức và ván đấu bị từ chối (`status: "rejected"`).




7. TRẢ KẾT QUẢ ĐỒNG BỘ (SYNC RESULT UX)
- Khi `sync-offline-rounds` trả về `SyncResult` với các ván bị `rejected` (do anti-cheat hoặc quá 7 ngày), Client cần hiển thị Summary Notification cho người chơi. VD: "Đã đồng bộ 18 ván, 2 ván không hợp lệ bị từ chối". Các ván rejected sẽ bị loại bỏ khỏi queue im lặng nếu không có thông báo này.
- Cảnh báo dung lượng hàng đợi: Nếu `queue.length > 150`, hiển thị cảnh báo đỏ trên UI yêu cầu người dùng kết nối mạng (tránh chạm giới hạn 200 dẫn đến FIFO đẩy ván cũ ra ngoài).
- Ưu tiên đồng bộ: Các ván chơi sắp quá hạn 7 ngày cần được xếp lên đầu batch đồng bộ (ưu tiên gửi trước).
- Cảnh báo sắp quá hạn: Nếu có ván offline nằm trong queue quá 6 ngày (sắp quá hạn 7 ngày), hiển thị thông báo khẩn cấp trước 24h để người chơi kịp online đồng bộ.

4. CHI TIẾT TRIỂN KHAI (IMPLEMENTATION DETAILS)
--------------------------------------------------------------------------------
4.1. Hệ thống Đa ngôn ngữ (i18n Engine):
- `LangContext` trong `i18n.ts` cung cấp context cho ngôn ngữ hiện tại (`lang`), hàm đảo ngôn ngữ (`toggle`), và dictionary (`t`).
- Để đảm bảo Vite Fast Refresh (HMR) hoạt động mượt mà không bị full page reload mỗi khi chỉnh sửa chuỗi bản dịch, các hằng số và context được tách riêng trong `i18n.ts`, còn React Provider nằm ở `lang-provider.tsx`.
- `vi.ts` và `en.ts` duy trì sự đồng bộ key (Key parity) tuyệt đối qua type assertion `export const en: typeof vi`. Hỗ trợ các hàm định dạng chuỗi động (Template functions) như:
  + `yrs_younger: (n: number) => string`
  + `brain_age_calibrating: (played: number, needed: number) => string`
  + `calibration_remaining: (remaining: number) => string`

4.2. Hệ thống Chủ đề & Style (Theme & Glassmorphism):
- `ThemeProvider` lưu theme lựa chọn vào `localStorage` với key `"[brand]-ui-theme"`. Khi theme là `"system"`, app dùng `window.matchMedia("(prefers-color-scheme: dark)")` để tự động chọn chế độ.
- Thao tác trực tiếp với DOM qua `root.classList.remove("light", "dark")` và `root.classList.add(...)`.
- Thiết kế UI kết hợp CSS Variables và Tailwind classes: `--neuro-panel-rgb`, `--neuro-cyan-rgb`, `--neuro-purple-rgb`, `--neuro-green-rgb`, `--neuro-red-rgb`, `--glass-blur`.
- Hiệu ứng kính mờ `backdrop-filter: blur(...)` kết hợp viền mỏng neon `border: 1px solid rgba(var(--neuro-cyan-rgb), 0.14)` giúp các card và thanh Dock giữ nguyên độ tương phản trên mọi nền ambient.

4.3. Thanh điều hướng nổi (Floating Dock):
- Cố định ở đáy màn hình `fixed bottom-0 left-1/2 -translate-x-1/2 z-40`.
- Sử dụng `env(safe-area-inset-bottom)` để tránh bị che bởi thanh điều hướng hệ điều hành iOS/Android.
- 5 tab điều hướng:
  + `dashboard` (LayoutDashboard, accent: #00D4FF - Cyan)
  + `play` (Gamepad2, accent: #A855F7 - Purple)
  + `history` (History, accent: #10B981 - Green)
  + `profile` (UserCog, accent: #F59E0B - Amber)
  + `god` (Terminal, accent: #00FF9C - Neon Green)
- Tooltip hiển thị phía trên icon khi hover (chỉ áp dụng trên Desktop `hidden sm:block`).
- Tự động ẩn Dock khi `RoundResultOverlay` hoặc `OnboardingOverlay` mở để tránh đè nút bấm hành động (CTA).

4.4. Quy trình Onboarding & Hiệu chuẩn (Calibration Baseline):
- Hằng số `CALIBRATION_TARGET = 5`.
- `OnboardingOverlay`: Modal 3 bước (Giới thiệu -> Hiệu chuẩn 5 ván -> Nhịp luyện tập). Hỗ trợ bấm phím `Escape` để đóng dialog.

4.5. Đấu trường & Tải game động (Play Arena & Dynamic Lazy Loading):
- `PlayArena` chia làm 2 tab: "Game Nhận Thức" (12 game) và "Arcade" (3 game offline).
- Map `GAME_COMPONENTS` ánh xạ từng `RoundGame` sang canonical wrapper component truyền `onComplete` và `onPlayStart`.
- `GameChunkFallback` hiển thị spinner `Loader2` trong lúc chunk JS của trò chơi đang tải qua mạng.
- Khi một game được chọn (`selectedGame`), giao diện chuyển sang chế độ sân chơi (`gameStageClass(selectedGame)`).
- Boundary được đặt bên ngoài `Suspense` để bắt được cả lỗi runtime crash trong game lẫn lỗi mạng khi tải chunk JS (network failure / stale chunk after deploy).

6. BẢO MẬT & VALIDATION (SECURITY & VALIDATION)
--------------------------------------------------------------------------------
6.1. Phân quyền Người dùng (Role & Permission Scoping):
- Chế độ Khách (Guest Mode): Kiểm tra qua `isGuestProfile(profile)`. Điểm số và tiến trình ván chơi được đồng bộ lên máy chủ y hệt người dùng thông thường (ADR-0007). Các tính năng cộng đồng như History và Quests bị vô hiệu hoá, Settings chỉ hiển thị các tuỳ chọn cơ bản cho đến khi nâng cấp tài khoản.
- Quyền Admin (Clearance Ω-1):
  + Chỉ hiển thị nút "God Mode" / Admin Panel trên FloatingDock nếu `profile.role === "admin"`.
  + Nếu người dùng không có quyền Admin cố tình truy cập tab "god", hệ thống chặn ngay lập tức và hiển thị `AccessDeniedOverlay` với mã cảnh báo "AUTHORIZATION LEVEL: INSUFFICIENT".

6.2. Validation dữ liệu phía Client (Client-side Validation):
- Avatar Upload: Kiểm tra file type (`image/jpeg`, `image/png`, `image/webp`, `image/gif`), giới hạn dung lượng file tối đa 2 MB trước khi gửi.
- Năm sinh (Birth Year): Bắt buộc là số nguyên `Number.isFinite(year)`, thuộc khoảng `year <= new Date().getFullYear() - 13`.
- Đổi mật khẩu: Kiểm tra độ dài tối thiểu 8 ký tự, bắt buộc nhập đúng mật khẩu hiện tại, kiểm tra `newPw === confirmPw`.
- Xoá tài khoản: Yêu cầu người dùng gõ chính xác từng ký tự tên đăng nhập (`deleteConfirm.trim().toLowerCase() === profile.username.toLowerCase()`) để tránh việc vô tình xoá tài khoản.

6.3. Bảo vệ Lỗi & Quyền riêng tư (Error Isolation & Telemetry):
- `ErrorBoundary` tự động cắt ngắn component stack trace (tối đa 400 ký tự) và loại bỏ thông tin nhạy cảm trước khi gửi sự kiện `ui.crash` lên server observability.
- Đảm bảo exception ở các phần tử giao diện con không làm lộ token hoặc dữ liệu cá nhân ra màn hình người dùng.




* CHÚ THÍCH: Mặc dù hệ thống đã rebrand thành MindGem, các key lưu trữ (localStorage, sessionStorage) như `[brand]-ui-theme`, `[brand].cached_profile`, `[brand].offline_queue`, `[brand].obs.session` được giữ nguyên tên cũ để không làm mất session và dữ liệu của người dùng hiện tại.*
